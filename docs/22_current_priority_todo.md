## 2. 先に解消する現状の矛盾

### C-1 前向き観察の名称と実体

再監査時の`run_forward_shadow.py`は将来結果を使う過去評価を不変JSONへ保存していた。`NOW-P0-1`〜`NOW-P0-4`で当日時点シグナル、短期・中期の継続口座、追記専用DB台帳、判断系統分離へ置き換えた。現在のジョブはMacの遅延DBだけを使う`delayed_historical`研究経路であり、正式な現在判断ではない。

推奨対応:

- 将来結果を使う旧画面経路は「過去評価」として分離して残す。
- Mac定期ジョブは遅延研究としてDBへ保存し、現在判断へ昇格させない。
- 正式な前向き運用期間へ算入するのは、新経路の品質ゲート完了後に固定した最初の営業日以降だけとする。

### C-2 短期・中期口座要件と通常モード

デモは短期・中期各250万円だが、再監査時の通常モードは`live_long_only`の1口座だった。`NOW-P0-2`で短期・中期の独立した継続口座状態を追加し、旧1口座は将来結果を使う過去評価として分離して残した。

推奨対応:

- 通常モードも短期・中期各250万円の独立口座にする。
- 口座ごとにルール、検証系列、現金、保有、損益、監査IDを分離する。

### C-3 ロードマップ表現と通常ジョブ

再監査時の`run_backtest.py`と`run_mid_term_analysis.py`はplaceholderでありながら`success`を記録していた。`NOW-P1-1`で通常バックテストを実データ用ウォークフォワードへ、`NOW-P1-2`で中期分析を時点整合サービスへ接続し、偽の成功を解消した。

推奨対応:

- 未実装またはデータ不足を成功扱いしない。
- `insufficient_data`、`skipped`、`error`、`success`を区別し、実サービスへ接続する。

### C-4 Macスケジュールとデータ所在

Raspberry Piが収集の正本DBを持つ一方、Mac LaunchAgentはMacへ最後に復元したDBを使用し、自動同期しない。

推奨対応:

- Macの現行実行は検証用・研究用と表示する。
- 正式運用はRaspberry Piへ単独移行し、Macと二重に正式実行しない。
- Raspberry Pi停止時にMacの古いDBから正式記録を代替生成しない。

### C-5 秘密情報方針と開発用既定値

`.env.example`の秘密値を空にする方針に対し、DBパスワードを含む既定接続文字列が存在する。

推奨対応:

- `.env.example`の秘密値を空にする。
- 必須値の未設定を起動前検証し、分かりやすく停止する。
- ログ、例外、テスト、バックアップへ秘密値が出ないことをテストする。
