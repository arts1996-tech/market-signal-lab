# 前向き仮想運用の実行主体と切替手順

## 現在の暫定運用: Macの遅延価格研究スナップショット

開発中はMacを遅延価格による過去評価スナップショットの暫定実行主体とする。これは正式な継続仮想口座や6〜12か月の前向き検証期間にはまだ算入しない。ユーザーLaunchAgent
`com.arts1996.market-signal-lab-forward-shadow`が、平日18:30、20:30、22:30に
`jobs/run_forward_shadow.py --daily --not-before-jst 18:30`を呼ぶ。

当日時点シグナル、短期・中期各250万円の独立口座、追記専用PostgreSQL台帳、`delayed_historical`／`current_market`のデータ分離、欠測・再試行・障害監視はMac側で完了した。Mac定期ジョブは18:30 JSTを同日再試行共通の判断時刻とし、遅延研究だけを短期・中期のDB台帳へ保存する。JSONは`data/forward_shadow/<account>/delayed_historical/YYYY-MM-DD.json`へDBから監査出力する。現在判断や正式な6〜12か月の前向き検証期間には算入しない。

- ログイン時にも呼び出すが、JST 18:30より前は正常終了して保存しない。
- 東証非営業日は保存しない。
- 当日分が保存済みなら、DB取得や分析の前に正常終了する。
- 18:30にMacがスリープしていた場合は復帰時にlaunchdが呼び出す。
- 電源OFF、ログアウト、Docker Desktop停止中は実行できない。20:30、22:30の再試行で補う。
- 翌日になってから前日の入力を再構成しない。取れなかった日は欠測として残す。
- Macとラズパイの自動ジョブを同時に正式運用しない。
- `job_runs`へ各試行の`started`と`success`／`skipped`／`error`を同じ試行IDで保存する。
- Dockerへ到達できずDBへ記録できない試行は`logs/forward-shadow-host-attempts.tsv`へ保存する。
- システム管理画面で当日2口座、最終成功、3回失敗、欠測、容量、JSON監査を確認する。
- 正式JSONはファイルハッシュ、連番、前レコードハッシュ、自身のハッシュを持つ`forward-audit-chain-v1`へ追記し、headで末尾切り詰めも検査する。
- 検証は`jobs/verify_audit_integrity.py`で独立実行し、`job_runs`へ投資結果とは別の運用結果として記録する。

## 将来の正式運用: Raspberry Pi

`docs/22_current_priority_todo.md`のNOW-P0品質ゲートが完了し、ラズパイを常時運用する段階では、正式な前向き仮想記録の実行主体をラズパイへ移す。
Macのlaunchdは開発用の手動確認だけに戻し、自動トリガーを停止する。

推奨するラズパイ側の構成は、Dockerコンテナを呼ぶoneshotのsystemd serviceと、
平日18:30、20:30、22:30のsystemd timerである。timerは`Persistent=true`とし、
ネットワークとDockerの起動後に実行する。ただし、翌日に前日分を後付け生成するのではなく、
ジョブ実行時のJST営業日だけを記録する。

ラズパイへの配置は、次をすべて満たしてからユーザー承認を得て実施する。

1. NOW-P0を完了し、Macで全テストと短期・中期の継続口座の日次記録を実営業日で確認する。
2. ラズパイDBの事前バックアップを取得する。
3. systemd service／timerをMacまたは隔離環境で構文確認する。
4. ラズパイへコードと設定を限定配置し、手動で1回試運転する。
5. ラズパイ側の日次JSON、ログ、終了コードを確認する。
6. MacのLaunchAgentを停止・無効化し、二重実行がないことを確認する。
7. 再起動後にラズパイのtimerが復旧することを確認する。

## 障害と欠測の扱い

- 最初に成功した当日スナップショットだけを不変記録とする。
- 同日の異なる入力で既存スナップショットを置換しない。
- 候補なし、品質ゲート未達も判断結果として保存する。
- すべての再試行が失敗した日は、翌日の価格やニュースで過去を作り直さない。
- 欠測日、Docker停止、DB停止、ディスク不足は運用警告として別途集計する。
- チェーン導入前のJSONは`--initialize-existing`でDB正本との一致を全件確認してから登録する。
- チェーン登録済みJSONの欠落・改変、連番欠落、順序変更、末尾削除、未登録JSONを検出した場合は自動追記と自動再出力を止める。調査後の復旧は証拠を保全して手動で行う。
- Raspberry Pi停止中の正式記録をMacの古いDBスナップショットで代替しない。

2026-08-22にMacの既存8件をDB正本と照合して初期チェーンへ登録し、独立再検証で`record_count=8`、`checked_file_count=8`、`anomaly_count=0`、`untracked_file_count=0`を確認した。チェーンとheadは同一ホスト上にあるため、管理権限を持つ攻撃者による全ファイルの整合的な再生成までは証明しない。必要になった時点で別ホストの署名済みアンカーを設計する。

この仕組みは実注文を行わず、投資助言または予測能力の証明には使用しない。
