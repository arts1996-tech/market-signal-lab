# 14 開発環境・実運用環境レビュー

## この文書の位置づけ
本文書は、`AGENTS.md` および `docs/02`, `docs/08`, `docs/09` に記載された開発環境・実運用環境の記述を整理し、懸念点をまとめた外部レビューである。
要件を変更するものではなく、既存仕様への補足・注意喚起として扱うこと。実装を担当するエージェントは、該当フェーズ（主にフェーズ1・フェーズ8）着手時に本文書を参照すること。

## 1. 開発環境（記載箇所: AGENTS.md, docs/02, docs/08）

- **開発マシン**: MacBook（Apple Silicon想定）上でCodexを使って開発する
- **開発ツール**: Docker / Docker Compose、Python 3.12、pytest
- **開発フロー**: Macでテスト → Git経由でRaspberry Piへ手動配置（docs/08「デプロイ」）
- **ARM64対応の維持**: Apple Silicon MacとRaspberry Pi OS 64-bitの両方で動作することが原則10（AGENTS.md）で明記されている
- **`.env`管理**: 開発時点から秘密情報はGit管理外とし、`.env.example`は値を空にする（docs/09）

## 2. 実運用環境（記載箇所: docs/02, docs/08, docs/09）

- **本番機**: Raspberry Pi 4、Raspberry Pi OS 64-bit
- **実行方式**: Docker Compose（`restart: unless-stopped`）でコンテナ常時稼働
- **永続化**: DBデータは可能な限りUSB SSDへ保存する（SDカードではなく）
- **サービス構成**: db(PostgreSQL) / dashboard(Streamlit) / collector / analyzer / gemini-agent / slack-bot / scheduler の7コンテナ想定
- **スケジューリング**: cronまたはsystemd timer。固定時刻依存を避けつつJST基準で1日8回程度のジョブを実行（06:30米国データ取得〜23:00バックアップ）
- **外部公開の扱い**: StreamlitとPostgreSQLは無制限にインターネット公開しない。外部アクセスはTailscale等を想定。SlackはSocket Mode（Pi側を外部公開しない）
- **監視・復旧**: ヘルスチェック、構造化ログ、ログローテーション、ディスク空き容量監視、DB容量監視、データ鮮度監視、失敗時のSlack通知
- **バックアップ**: `pg_dump`によるSSDへの日次保存、保存期間設定、古いバックアップの削除、リストア手順のREADME記載

## 3. 懸念点

### 3.1 Pi 4(8GB)へのリソース負荷が未検証
7コンテナ（PostgreSQL含む）+ 定期分析ジョブ + Gemini/Slack常時待受を1台のPi 4で同時に稼働させる設計だが、CPU/メモリの見積もりやDocker Composeでのリソース制限（`mem_limit`等）の記載がない。バックテストや相関計算はデータ量次第でメモリを消費する可能性があり、実装が進んでから問題が顕在化するリスクがある。フェーズ1完了時点で一度リソース使用量を実測することを推奨する。

### 3.2 SSDの接続方式・電源が未記載
「USB SSDへ保存」とあるが、USB経由の給電不足はRaspberry Piで定番のトラブル要因であり、電圧不足によるSSD切断やDB破損につながりうる。公式電源アダプタの使用、USBブートか外付けストレージとしての利用かなど、具体的な構成がdocs/08に記載されていない。運用ドキュメントに一言追記しておくことを推奨する。

### 3.3 Tailscaleの具体的な組み込みが未定義
「外部アクセスはTailscale等を想定」とあるのみで、Slack Bot（Socket Mode）以外に、外出先からStreamlitダッシュボードへアクセスする手段としてどう使うか、Docker Composeへの組み込み方が未定義。フェーズ8着手時に具体化する必要がある。

### 3.4 開発環境と実運用環境でのマイグレーション運用差異
AlembicによるDBマイグレーションはdocs/07で言及されているが、Macで確認したマイグレーションを本番Pi側のDBへどう適用するか（自動適用か手動確認か）の手順が明記されていない。本番DBを壊さないための最終確認ステップを明文化することを推奨する。

### 3.5 障害時のフォールバック範囲が限定的
Gemini停止時のPython縮退運転（docs/05）やAPI再試行（docs/09）は定義されているが、Raspberry Pi本体の電源断・SDカード/SSD故障からの「自動復旧」（docs/02の非機能要件に記載）について、具体的な実装方法（例: systemdによる起動時のDocker Compose自動起動）が未定義。フェーズ8の受け入れ基準に「再起動後、手動操作なしで全サービスが復旧すること」のような具体的なテスト項目を追加することを推奨する。

### 3.6 ログへの秘密情報混入チェックが自動化されていない
docs/09で「ログへ秘密情報を出さない」という方針は示されているが、これを担保する仕組み（ログ出力のマスキング処理、レビュー方法）がテスト項目（docs/09「テスト」節）に含まれていない。トークンや`.env`の値がログに漏れていないかを検査するテスト・CI項目を追加することを推奨する。

## 4. まとめ
開発環境（Mac）と実運用環境（Raspberry Pi）の分離、およびARM64対応・Docker Compose統一という基本方針は妥当である。一方で、実運用環境側の物理的な制約（Pi 4のリソース、SSDの電源、Tailscale統合、障害時の自動復旧）に関する記載が薄く、フェーズ8「Raspberry Pi本番化」着手前にこれらを具体化しておく必要がある。特に3.1・3.2・3.5は、実際の運用中にデータ欠損やDB破損として顕在化しやすい項目であるため優先度を高めに扱うことを推奨する。
